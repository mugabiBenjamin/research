## Description / Context

Provide background on the feature, bug, or task. Explain the system or workflow it relates to so a new contributor can orient themselves without needing to ask questions.

Explain the impact of this issue — on users, the product, system reliability, performance, or business operations. Make the case for why this work is worth prioritising.

## Origin and Evidence

Describe where this issue came from. Include links to bug reports, support tickets, monitoring alerts, user feedback, or prior discussions. Attach logs, screenshots, or reproduction steps where relevant.

## Expected Behaviour

Describe what should happen. Be precise — this becomes the reference point for reviewers and testers.

## Actual Behaviour

Describe what currently happens instead. Include error messages, incorrect outputs, or missing functionality as observed.

## Proposed Solution

Outline the intended approach to resolving the issue. This does not need to be final, but should give an implementer enough direction to begin. Note any alternatives considered and why they were set aside.

## Acceptance Criteria

The issue can only be considered complete when:

- [ ] All specified requirements are implemented.
- [ ] Relevant tests pass.
- [ ] No existing functionality is broken.
- [ ] Error handling is implemented where necessary.
- [ ] Documentation is updated where applicable.
- [ ] Changes are reviewed and approved through a pull request.
